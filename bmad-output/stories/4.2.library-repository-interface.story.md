# 4.2: `LibraryRepository` interface, `LibraryService` and `LocalRepository`

**Story ID:** 4.2  
**Epic:** 4 — Library packages and catalogue (editor)  
**Slug:** library-repository-interface  
**Status:** ready-for-dev   <!-- lifecycle: backlog -> ready-for-dev -> in-progress -> review -> done -->

> Owned by planning until `ready-for-dev`. Sized to one dev-day (~2-8h). No story points.

## Story

As **the STIx Config developer**,  
I want **one service that provides packages regardless of where they come from**,  
so that **the controller and shop sources can be added later without touching the editor**.

## Acceptance Criteria

<!-- LOCKED. Numbered, testable. External dev tools must not edit. -->

1. `LibraryRepository_class` (abstract) declares `list()`, `fetchDescriptor(uuid, vers)`, `fetchPackage(uuid, vers)`, `install(pkg)`, `remove(uuid, vers)`; it is asynchronous (results via signals) so network repositories fit.
2. `LocalRepository` serves the packages in `templates/` (development, read-only) and in `AppLocalDataLocation/libraries/<Kind>/<Uuid>/<Vers>/`.
3. `LibraryService_class` (L3) combines repositories and exposes a QML-visible catalogue model `{uuid, name, kind, vers, source, signed}`.
4. `main.cpp` registers it as `STI.LibraryService`.
5. No code outside LibraryService reads the library folders directly (a grep check).

## Dev Notes

<!-- LOCKED. Cited guidance. [Inference] marks judgement calls not stated in the planning docs. -->

- L3 defines `LibraryRepository_class` with `list()`, `fetchDescriptor`, `fetchPackage`, `install`, `remove`; implementations `LocalRepository` (MVP), `ControllerRepository` (MVP, FR-15), `ShopRepository` (post-MVP). [Source: architecture.md#adr-012]
- `LibraryService_class` combines them and feeds `BlockManager` and `SchemaManager`. UI code never reads library folders directly. [Source: architecture.md#adr-012]
- A package installed locally is unpacked to `AppLocalDataLocation/libraries/<Kind>/<Uuid>/<Vers>/`; several versions live side by side. [Source: architecture.md#adr-004]
- Singletons registered in `main.cpp` under `STI.<Name>`. [Source: architecture.md#adr-009]
- Paths come from `QStandardPaths` (`Setup.hpp` already defines `CACHE_APP_PATH`). [Inference] [Source: architecture.md#adr-013]
