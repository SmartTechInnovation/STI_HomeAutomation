# 2.3: Golden fixture projects per released `ConfigVers`

**Story ID:** 2.3  
**Epic:** 2 — Project file format v1.0.0  
**Slug:** golden-fixtures  
**Status:** ready-for-dev   <!-- lifecycle: backlog -> ready-for-dev -> in-progress -> review -> done -->

> Owned by planning until `ready-for-dev`. Sized to one dev-day (~2-8h). No story points.

## Story

As **the STIx Config developer**,  
I want **a sample project for every released format version that must always open**,  
so that **backward compatibility is guarded automatically, not by memory**.

## Acceptance Criteria

<!-- LOCKED. Numbered, testable. External dev tools must not edit. -->

1. `tests/fixtures/projects/1.0.0/Project.xml` contains every element kind of the 1.0.0 data model: `Requires/Library`, `Rooms`, `Variables`, `RootDevice` with sections and channels, `Program/Page` with a `BlockInstance` (an `Input` with **two** `Source`s, an `Output`, a `Property`), `SignalInRef`, `SignalOutRef`, and one unknown element.
2. A test loops over **every** folder in `tests/fixtures/projects/`, opens each project without errors, saves it to a temp dir, and re-opens it.
3. For the current version the saved file is byte-identical to the fixture (apart from `MDate`); for older versions the test checks that migration ran.
4. The fixture follows the 2.1 style rules, so it doubles as a readable example of the format.

## Tasks / Subtasks

- [ ] Write the 1.0.0 fixture by hand from §5 of the architecture (AC: #1, #4)
- [ ] Write `tst_goldenprojects` with folder discovery (AC: #2, #3)

## Dev Notes

<!-- LOCKED. Cited guidance. [Inference] marks judgement calls not stated in the planning docs. -->

- Every released `ConfigVers` has a sample project under `tests/fixtures/projects/<version>/`, and the testing strategy requires each one to open. [Source: architecture.md#adr-003]
- Use the illustrative 1.0.0 Project.xml and the entity table as the source of the fixture content, including two sources on one input. [Source: architecture.md#5-data-model]
- Golden files are the guard for NFR-03 (old files always open). [Source: architecture.md#0-requirements-baseline]
- Releasing a new format version later = add a folder; no test code changes. [Inference]

## Testing

<!-- LOCKED. STRATEGY ONLY — what to verify and how. Never run tests or quote coverage here. -->

- **Approach:** a data-driven Qt Test (`QFETCH` per folder).
- **Key scenarios:** all fixtures open and round-trip.
- **Per-AC verification:** AC #1 → review the fixture against the data model table; AC #2 → count of tested folders == count of folders; AC #3 → byte compare; AC #4 → manual read-through
- **Fixtures / mocks:** this story *is* the fixture.
- **Edge cases to cover:** a fixture folder without Project.xml → test fails clearly.
