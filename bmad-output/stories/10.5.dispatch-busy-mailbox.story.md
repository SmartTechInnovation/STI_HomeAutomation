# 10.5: Inline dispatch with per-instance `busy` flag, mailbox and loop guard

**Story ID:** 10.5  
**Epic:** 10 — STIx Runtime MVP (separate repository `stix-runtime`)  
**Slug:** dispatch-busy-mailbox  
**Status:** ready-for-dev   <!-- lifecycle: backlog -> ready-for-dev -> in-progress -> review -> done -->

> Owned by planning until `ready-for-dev`. Sized to one dev-day (~2-8h). No story points.

## Story

As **the controller**,  
I want **values to reach their targets instantly from any thread without locks or deadlocks**,  
so that **drivers react immediately and blocks stay simple single-threaded code**.

## Acceptance Criteria

<!-- LOCKED. Numbered, testable. External dev tools must not edit. -->

1. `emit` (block output) and `emit_signal` (driver channel) store the value and call each subscriber's `on_input(input_idx, source_id, value)` inline on the calling thread.
2. Each instance has an atomic `busy` flag and a lock-free mailbox: free → the calling thread runs it inline; busy → the event is queued, and the holding thread drains the mailbox before releasing. One instance never runs on two threads at once; no thread ever waits on a lock.
3. A per-thread loop guard stops a chain deeper than `MaxDepth` (64) or longer than `MaxCalls` (10,000) per event, quarantines the instance re-entered most, and reports a fault (`iUuid`s of the chain).
4. No heap allocation in dispatch (mailboxes preallocated at load).
5. A multi-thread stress test (several threads emitting into shared blocks for 60 s) shows no instance entered twice concurrently, no deadlock, no lost event.

## Dev Notes

<!-- LOCKED. Cited guidance. [Inference] marks judgement calls not stated in the planning docs. -->

- Threads that run block code: every driver thread (`emit_signal`) and the RuntimeManager (`run()` ticks, Force/SetVariable). Per-instance serialisation by the runtime: atomic `busy` flag + small lock-free mailbox; free → run inline; busy → mailbox, drained by the holder; one compare-and-swap per call. [Source: architecture.md#adr-005]
- LOCKED: the runtime must not replace the busy flag/mailbox with mutexes (driver 1 inside A calls B while driver 2 inside B calls A would deadlock). [Source: architecture.md#adr-005]
- Loop guard in thread-local RAM: `MaxDepth` 64, `MaxCalls` 10,000; a loop back to a busy instance goes to its mailbox, so an endless loop shows as an endless number of calls, not a stack overflow. [Source: architecture.md#adr-005]
- Accepted by design: a block reached by two paths runs twice; signals are not synchronised. [Source: architecture.md#adr-005]
- NFR-01 target: < 1 ms from driver event to output through 1,000 callbacks on a Cortex-A53-class CPU. [Source: architecture.md#0-requirements-baseline]

## Testing

- **Approach:** unit tests, a multi-thread stress test (TSan build in CI), a micro-benchmark.
- **Key scenarios:** inline; contention; A→B→A loop; 1,000-callback chain timing.
- **Per-AC verification:** AC #1 → call order test; AC #2 → TSan clean + concurrent-entry detector; AC #3 → loop plugin quarantined with chain; AC #4 → allocation counter; AC #5 → 60 s stress job

- **Edge cases to cover:** a block emitting to itself; mailbox full (size from fan-in at load).
