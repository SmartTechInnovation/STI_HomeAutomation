# 6.4: Pin the controller certificate on first connection

**Story ID:** 6.4  
**Epic:** 6 — Controller connection (editor side)  
**Slug:** certificate-pinning  
**Status:** ready-for-dev   <!-- lifecycle: backlog -> ready-for-dev -> in-progress -> review -> done -->

> Owned by planning until `ready-for-dev`. Sized to one dev-day (~2-8h). No story points.

## Story

As **an integrator**,  
I want **to confirm a controller's identity once and be warned if it ever changes**,  
so that **nobody can impersonate my controller**.

## Acceptance Criteria

<!-- LOCKED. Numbered, testable. External dev tools must not edit. -->

1. On first connection to a serial, the editor shows the certificate SHA-256 fingerprint and the serial; accepting stores it in `AppLocalDataLocation/trust/controllers/<serial>.pin`.
2. Later connections succeed only if the certificate matches the pin; a mismatch is a hard error with a "Re-pair" action that requires typing the serial to confirm.
3. Declining the fingerprint closes the connection and stores nothing.
4. A CA-signed controller certificate (optional STI Device CA) is accepted when the CA is in the trust store, and is still pinned.

## Dev Notes

<!-- LOCKED. Cited guidance. [Inference] marks judgement calls not stated in the planning docs. -->

- On first boot each controller generates a key pair and a self-signed certificate (later optionally STI Device CA). The first time the editor connects it shows the fingerprint; once accepted, the certificate is **pinned** per controller serial in `AppLocalDataLocation/trust/`. A changed certificate is a hard error with an explicit re-pair flow. [Source: architecture.md#adr-008]
- Trade-off: pinning (TOFU) by default; the fingerprint is printed on the device label or console. [Source: architecture.md#9-trade-off-analysis]
- Modal dialogs are allowed here because trust is a security decision (equivalent to a data-loss prompt). [Inference] [Source: architecture.md#adr-010]

## Testing

<!-- LOCKED. STRATEGY ONLY — what to verify and how. Never run tests or quote coverage here. -->

- **Approach:** integration tests with the mock using two certificates.
- **Key scenarios:** first pin, match, mismatch, re-pair, decline.
- **Per-AC verification:** AC #1 → pin file created; AC #2 → swap the mock cert → error; AC #3 → decline → no file; AC #4 → test CA fixture
- **Fixtures / mocks:** two self-signed certs and one CA-signed cert.
- **Edge cases to cover:** a corrupt pin file.
