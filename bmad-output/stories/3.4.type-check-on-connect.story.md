# 3.4: Refuse incompatible connections

**Story ID:** 3.4  
**Epic:** 3 — Wiring and validation in the editor  
**Slug:** type-check-on-connect  
**Status:** ready-for-dev   <!-- lifecycle: backlog -> ready-for-dev -> in-progress -> review -> done -->

> Owned by planning until `ready-for-dev`. Sized to one dev-day (~2-8h). No story points.

## Story

As **an integrator**,  
I want **STIx Config to stop me from wiring incompatible data types**,  
so that **type errors never reach the controller**.

## Acceptance Criteria

<!-- LOCKED. Numbered, testable. External dev tools must not edit. -->

1. `cmdConnect` refuses a connection when `DataTypes::canConnect(sourceType, targetType)` is false, returning `false` with `ErrorCode_e::TypeMismatch` and a message naming both types.
2. While dragging a wire, incompatible input ports are visibly dimmed, using a `Q_INVOKABLE canConnectTo(sourceIUuid, targetIUuid)` from C++.
3. Source and target types are resolved from the block descriptor (ports), the signal channel or the variable `DataType`.
4. The conversion matrix is the existing one: Bool↔Int↔Float convertible; String, Enum, Date and Custom only to themselves.

## Tasks / Subtasks

## Testing

<!-- LOCKED. STRATEGY ONLY — what to verify and how. Never run tests or quote coverage here. -->

- **Approach:** unit tests plus a manual UI check.
- **Key scenarios:** Bool→Float ok, String→Bool refused.
- **Per-AC verification:** AC #1 → refused connect + error code; AC #2 → drag over a String input: dimmed; AC #3 → fixture with each source kind; AC #4 → table-driven test over the matrix

- **Edge cases to cover:** an unknown DataType → refused, logged.
