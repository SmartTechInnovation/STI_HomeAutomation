# 10.1: Runtime repository skeleton and cross-build CI

**Story ID:** 10.1  
**Epic:** 10 — STIx Runtime MVP (separate repository `stix-runtime`)  
**Slug:** runtime-skeleton  
**Status:** ready-for-dev   <!-- lifecycle: backlog -> ready-for-dev -> in-progress -> review -> done -->

> Owned by planning until `ready-for-dev`. Sized to one dev-day (~2-8h). No story points.

## Story

As **the runtime developer**,  
I want **a buildable `stix-runtime` repository with its dependencies and CI for all controller targets**,  
so that **every runtime story starts from a working build**.

## Acceptance Criteria

<!-- LOCKED. Numbered, testable. External dev tools must not edit. -->

1. `stix-runtime/` has CMake (C++17, no Qt), and pulls pugixml, tinycbor and OpenSSL 3 with pinned versions.
2. It vendors or submodules `stix-sdk` (`stix_abi.h`, `stix_tokens.h`) at a pinned commit.
3. CI builds for linux-x86_64 (native, runs the tests), linux-aarch64 and linux-armv7hf (cross), with warnings as errors.
4. A unit test framework (e.g. doctest or GoogleTest — record the choice in decision-log.md) runs on x86-64 in CI.
5. The repository is licensed per ADR-014 (LGPL-3.0 or Apache-2.0, as decided) with a LICENSE file.

## Tasks / Subtasks

- [ ] Repository + CMake + dependencies (AC: #1, #2)
- [ ] CI matrix (AC: #3)
- [ ] Test framework (AC: #4)
- [ ] Licence (AC: #5)

## Dev Notes

<!-- LOCKED. Cited guidance. [Inference] marks judgement calls not stated in the planning docs. -->

- Runtime: C++17, no Qt, OpenSSL 3, pugixml; runtime CBOR with tinycbor. [Source: architecture.md#8-technology-stack]
- Products share only `stix-sdk` headers; the runtime is a separate repo on Linux. [Source: architecture.md#adr-001]
- Licensing: Runtime LGPL-3.0 or Apache-2.0 so proprietary plugins create no GPL obligations; SDK MIT. [Source: architecture.md#adr-014]
- Controller targets: linux-aarch64, linux-armv7hf, linux-x86_64. [Source: architecture.md#adr-004]
