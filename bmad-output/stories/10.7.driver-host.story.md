# 10.7: Driver host: driver threads, `open`/`close`/`write`

**Story ID:** 10.7  
**Epic:** 10 — STIx Runtime MVP (separate repository `stix-runtime`)  
**Slug:** driver-host  
**Status:** ready-for-dev   <!-- lifecycle: backlog -> ready-for-dev -> in-progress -> review -> done -->

> Owned by planning until `ready-for-dev`. Sized to one dev-day (~2-8h). No story points.

## Story

As **a driver author**,  
I want **the runtime to start my driver on its own thread and route outputs to `write`**,  
so that **hardware is read and written promptly**.

## Acceptance Criteria

<!-- LOCKED. Numbered, testable. External dev tools must not edit. -->

1. For each driver instance the runtime calls `open()`; the driver creates its own thread(s) and calls `emit_signal(channel, value)` when values arrive.
2. When a chain reaches an output signal, the runtime calls that driver's `write(channel, value)` directly from the running thread.
3. On project swap or shutdown, `close()` is called and the driver's threads must end within 2 s (otherwise logged as a fault).
4. The virtual-io reference driver (5.4) works end to end: a forced virtual input reaches a block and a virtual output.

## Tasks / Subtasks

- [ ] open/close lifecycle (AC: #1, #3)
- [ ] write routing (AC: #2)
- [ ] End-to-end test with virtual-io (AC: #4)

## Dev Notes

<!-- LOCKED. Cited guidance. [Inference] marks judgement calls not stated in the planning docs. -->

- One way to send a signal: `host->emit_signal(channel, value)`; callbacks run inline on the calling thread; no runtime event queue; polling (e.g. Modbus per-channel `PollMs`) is the driver's job. [Source: architecture.md#adr-005]
- Output signals: the runtime calls the driver's `write` directly from whichever thread is running; `write` must be thread-safe and non-blocking (SDK queue adapter). [Source: architecture.md#adr-005]
- Each driver configured twice is two instances, each with its own connection and thread. [Source: architecture.md#1-system-overview]

## Testing

<!-- LOCKED. STRATEGY ONLY — what to verify and how. Never run tests or quote coverage here. -->

- **Approach:** integration tests with virtual-io and a fake hardware driver.
- **Key scenarios:** open, emit, write, close, a hanging close.
- **Per-AC verification:** AC #1 → thread started, emit reaches a block; AC #2 → write called; AC #3 → close timeout → fault; AC #4 → end-to-end
- **Fixtures / mocks:** 5.4 virtual-io; a `slow-close` test driver.
- **Edge cases to cover:** write called during close.
