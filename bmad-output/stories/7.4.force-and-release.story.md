# 7.4: Force and release signals

**Story ID:** 7.4  
**Epic:** 7 — Live monitoring and force  
**Slug:** force-and-release  
**Status:** ready-for-dev   <!-- lifecycle: backlog -> ready-for-dev -> in-progress -> review -> done -->

> Owned by planning until `ready-for-dev`. Sized to one dev-day (~2-8h). No story points.

## Story

As **an integrator**,  
I want **to force a signal or input to a value and release it again**,  
so that **I can simulate inputs and test the logic in real time**.

## Acceptance Criteria

<!-- LOCKED. Numbered, testable. External dev tools must not edit. -->

1. From a port or signal context menu, "Force…" opens a value editor matching the type and sends `Force {slot, value, persistent}`; "Release" sends `Release {slot}`; "Release all" is in the top bar.
2. Forced items are flagged until released (7.3 badge).
3. Forces are released on disconnect unless "persistent" was chosen; persistent forces are listed when reconnecting.
4. The actions are enabled only for the Engineer role and above.

## Tasks / Subtasks

- [ ] Context menu + typed editor (AC: #1)
- [ ] Release all (AC: #1)
- [ ] Persistent handling on reconnect (AC: #3)
- [ ] Role gating (AC: #4)

## Dev Notes

<!-- LOCKED. Cited guidance. [Inference] marks judgement calls not stated in the planning docs. -->

- Forced values are visibly flagged in the UI and the controller's audit log, and are released on disconnect unless set as "persistent". [Source: architecture.md#adr-008]
- `Force {slot, value, persistent}`, `Release {slot}` or `{all:true}`, role Engineer. [Source: architecture.md#6-1-stix-link-messages-protocol-v1]
- The RuntimeManager applies forced values with the same `emit_signal` path. [Source: architecture.md#adr-005]
