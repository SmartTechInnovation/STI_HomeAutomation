# 3.2: Implement `Page_class::connections()`

**Story ID:** 3.2  
**Epic:** 3 — Wiring and validation in the editor  
**Slug:** page-connections-model  
**Status:** ready-for-dev   <!-- lifecycle: backlog -> ready-for-dev -> in-progress -> review -> done -->

> Owned by planning until `ready-for-dev`. Sized to one dev-day (~2-8h). No story points.

## Story

As **the editor UI**,  
I want **a list of every wire on the active page that updates when the document changes**,  
so that **the canvas can draw the connections**.

## Acceptance Criteria

<!-- LOCKED. Numbered, testable. External dev tools must not edit. -->

1. `Page_class::connections()` returns one entry per `Source` on the page: `{sourceIUuid, sourceOwnerIUuid, targetIUuid, targetOwnerIUuid, dataType}`.
2. The list updates through the existing `nodeInserted` / `nodeRemoved` / `attributeChanged` signals and emits `connectionsChanged` only when the page's wires changed.
3. A source that lives on another page (a cross-page reference) is included with a flag `external: true`.
4. Building the list doesn't walk the whole project tree: it uses the page's own caches and the project's `IUuid` index.

## Tasks / Subtasks

- [ ] Maintain a per-page cache of Source nodes in `onInserted` / `onRemoved` (AC: #2, #4)
- [ ] Build the entries (AC: #1, #3)
- [ ] Tests with a QSignalSpy (AC: #1, #2, #3)

## Dev Notes

<!-- LOCKED. Cited guidance. [Inference] marks judgement calls not stated in the planning docs. -->

- View models such as `Page_class` and `ProjectTree_class` are *caches* rebuilt from signals; the XML tree is the only source of truth. [Source: architecture.md#adr-002]
- `Page_class::connections()` is still a stub today. [Source: architecture.md#component-project-l2]
- Editor performance target: 60 fps pan/zoom with 500 blocks on a page. Per-page caching avoids walking the whole tree. [Source: architecture.md#0-requirements-baseline] [Source: architecture.md#7-fr--nfr-coverage-matrix]
- Use `Project_class::getNode(iUuid)` (existing index) to resolve the owners. [Inference] (from project.h)

## Testing

<!-- LOCKED. STRATEGY ONLY — what to verify and how. Never run tests or quote coverage here. -->

- **Approach:** unit tests.
- **Key scenarios:** connect/disconnect updates the list; changes on other pages don't emit.
- **Per-AC verification:** AC #1 → compare the list to the expected entries; AC #2 → spy count per change; AC #3 → fixture with a cross-page Ref; AC #4 → review + a micro-benchmark on 500 blocks
- **Fixtures / mocks:** a 2-page fixture.
- **Edge cases to cover:** a dangling Ref (target missing) → entry omitted, warning once.
