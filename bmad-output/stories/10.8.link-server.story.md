# 10.8: Link server: TLS, framing, `Hello`, `Auth`, roles, `GetInfo`

**Story ID:** 10.8  
**Epic:** 10 — STIx Runtime MVP (separate repository `stix-runtime`)  
**Slug:** link-server  
**Status:** ready-for-dev   <!-- lifecycle: backlog -> ready-for-dev -> in-progress -> review -> done -->

> Owned by planning until `ready-for-dev`. Sized to one dev-day (~2-8h). No story points.

## Story

As **the controller**,  
I want **to accept STIx Link connections securely**,  
so that **STIx Config (and later STIx HMI) can manage and monitor it**.

## Acceptance Criteria

<!-- LOCKED. Numbered, testable. External dev tools must not edit. -->

1. A TLS 1.3 server (OpenSSL) on `PortLink` (default 9443) uses the controller's key pair, generated on first boot with a self-signed certificate.
2. Frames are `uint32 len | CBOR {t,id,p}` (tinycbor), with a size limit; it is compatible with the STIx Config codec (shared test vectors).
3. `Hello` negotiates the protocol version; `Auth` checks Argon2id-hashed accounts and issues session tokens with roles; every other request is checked against the role table.
4. `GetInfo` returns state, project hash, title, `rev`, uptime, CPU, memory.
5. Connections are handled off the RuntimeManager thread; the server never blocks dispatch.

## Dev Notes

<!-- LOCKED. Cited guidance. [Inference] marks judgement calls not stated in the planning docs. -->

- STIx Link: TLS 1.3 over TCP, `uint32 len | CBOR {t,id,p}`, request/response + push, chunked transfers, protocol version in `Hello`. [Source: architecture.md#adr-007]
- Controller identity: key pair + self-signed cert on first boot; accounts with Argon2id hashes; RBAC Admin/Engineer/Viewer (+ HmiUser); every request except Hello/Auth carries an authorised session. [Source: architecture.md#adr-008]
- Role per message: the §6.1 table is the policy. [Source: architecture.md#6-1-stix-link-messages-protocol-v1]
- Reuse the frame test vectors produced by STIx Config story 6.1, so both codecs stay byte-compatible. [Inference]

## Testing
