# 9.2: Three-way merge engine (engineer wins)

**Story ID:** 9.2  
**Epic:** 9 — Project sync and merge  
**Slug:** three-way-merge-engine  
**Status:** ready-for-dev   <!-- lifecycle: backlog -> ready-for-dev -> in-progress -> review -> done -->

> Owned by planning until `ready-for-dev`. Sized to one dev-day (~2-8h). No story points.

## Story

As **the STIx Config developer**,  
I want **a pure, tested function that merges Base, Mine and Controller**,  
so that **users' changes on the controller and the engineer's work are combined correctly**.

## Acceptance Criteria

<!-- LOCKED. Numbered, testable. External dev tools must not edit. -->

1. `mergeProjects(base, mine, controller)` (pure function on `XmlNode_class` trees) returns a change set to apply to Mine, plus a summary.
2. Per element (matched by `IUuid`) and attribute: changed only on the controller → take the controller value; changed only in Mine → keep; changed on both → **Mine (engineer) wins**, and the case is listed in the summary as "user value replaced".
3. Structure always comes from Mine: elements added or deleted in Mine stay so; an instance deleted in Mine but changed on the controller is listed in the summary.
4. Elements without `IUuid` are compared by position under their parent; ambiguous cases keep Mine and are listed.
5. Merging 1,000 instances takes under 200 ms.

## Tasks / Subtasks

- [ ] Index the trees by IUuid (AC: #1)

- [ ] Structure rules (AC: #3)
- [ ] Fallback for elements without IUuid (AC: #4)
- [ ] Tests + benchmark (AC: #2, #3, #4, #5)

## Dev Notes

<!-- LOCKED. Cited guidance. [Inference] marks judgement calls not stated in the planning docs. -->

- Three-way merge by `IUuid`: Base = exact XML of the last upload (kept by the controller); Mine = open project; Controller = current. Per element and attribute: unchanged/changed → controller value; changed/unchanged → mine; both, same → no conflict; both, different → **the engineer's value wins**; structure always from Mine. [Source: architecture.md#adr-017]
- The merge is fully automatic, with a summary ("14 values taken from the controller; 2 user values replaced by yours"). [Source: architecture.md#adr-017] [Source: decision-log.md#adr-017-merge-rule]
- Only attribute values of existing elements can change on the controller. [Source: architecture.md#adr-017]
- Keep it in L2 (`src/Components/Project/Merge/`) with no Link dependency, so it is unit-testable in isolation. [Inference]

## Testing

<!-- LOCKED. STRATEGY ONLY — what to verify and how. Never run tests or quote coverage here. -->

- **Approach:** table-driven unit tests on small XML trees, plus a benchmark.
- **Key scenarios:** every row of the merge table; deletion vs change; no-IUuid elements.
- **Per-AC verification:** AC #1 → API test; AC #2 → one test per rule; AC #3 → deletion case; AC #4 → position fallback; AC #5 → benchmark fixture
- **Fixtures / mocks:** `tests/fixtures/merge/<case>/{base,mine,controller,expected}.xml`.
- **Edge cases to cover:** Mine and Controller identical; Base missing (→ refuse, needs Base).
