# 4.5: Verify package signatures (Ed25519)

**Story ID:** 4.5  
**Epic:** 4 — Library packages and catalogue (editor)  
**Slug:** package-signature-verify  
**Status:** ready-for-dev   <!-- lifecycle: backlog -> ready-for-dev -> in-progress -> review -> done -->

> Owned by planning until `ready-for-dev`. Sized to one dev-day (~2-8h). No story points.

## Story

As **an integrator**,  
I want **STIx Config to tell me whether a package is signed by a trusted publisher**,  
so that **I never install a tampered package by accident**.

## Acceptance Criteria

<!-- LOCKED. Numbered, testable. External dev tools must not edit. -->

1. `SIGNATURE` (Ed25519 over the manifest + file hashes) is verified against a trusted key list (the STI shop key + keys the user adds) during install.
2. An invalid signature refuses the install; a **missing** signature installs only after an explicit "unsigned development package" confirmation, and the package is marked `signed: false`.
3. The trusted keys live in `AppLocalDataLocation/trust/packages/` and can be added or removed from the library manager.
4. The verification code is isolated behind one function so the crypto library can be swapped.

## Tasks / Subtasks

- [ ] Choose and integrate the Ed25519 implementation (OpenSSL 3 EVP or libsodium); add a decision-log entry (AC: #1, #4)
- [ ] Verification in the install path (AC: #1, #2)
- [ ] Trusted key store (AC: #3)
- [ ] Tests with a test key pair (AC: #1, #2)

- A new dependency beyond Qt needs an ADR or decision-log entry. [Source: architecture.md#adr-013]

## Testing

<!-- LOCKED. STRATEGY ONLY — what to verify and how. Never run tests or quote coverage here. -->

- **Key scenarios:** valid, tampered, unsigned, unknown key.
- **Per-AC verification:** AC #1 → valid → installed, signed: true; AC #2 → tampered byte → refused; AC #3 → unsigned → confirmation path; AC #4 → add/remove a key
- **Fixtures / mocks:** a test key pair committed under tests/fixtures (test-only).
- **Edge cases to cover:** a key file in the wrong format.
