# 6.5: Login, roles and session

**Story ID:** 6.5  
**Epic:** 6 — Controller connection (editor side)  
**Slug:** auth-and-session  
**Status:** ready-for-dev   <!-- lifecycle: backlog -> ready-for-dev -> in-progress -> review -> done -->

> Owned by planning until `ready-for-dev`. Sized to one dev-day (~2-8h). No story points.

## Story

As **an integrator**,  
I want **to log in to the controller with my account**,  
so that **only authorised people can change the installation**.

## Acceptance Criteria

<!-- LOCKED. Numbered, testable. External dev tools must not edit. -->

1. After `Hello`, a login dialog sends `Auth {user, password}`; on success `ControllerLink.roles` holds the roles (Admin, Engineer, Viewer).
2. The password is never stored. The session token may be stored in the OS keychain when QtKeychain is available (optional build flag); otherwise the user logs in again.
3. UI actions are enabled according to the role (e.g. Upload needs Engineer); a refused request (`Forbidden`) is shown clearly.
4. An expired session leads back to the login dialog without losing the connection state.

## Tasks / Subtasks

- [ ] Auth request + roles property (AC: #1)
- [ ] Optional QtKeychain integration (AC: #2)
- [ ] Role-based enabling helper for QML (AC: #3)
- [ ] Expiry handling (AC: #4)

## Dev Notes

<!-- LOCKED. Cited guidance. [Inference] marks judgement calls not stated in the planning docs. -->

- A controller account (username + password, Argon2id hash on the controller) is exchanged for a session token in `Auth`; the password is only ever sent inside TLS. The editor never stores passwords and may keep the token in the OS keychain (`QtKeychain`, optional). [Source: architecture.md#adr-008]
- Roles: Admin (accounts, packages, upload), Engineer (upload, force, set variables), Viewer (monitor only); the controller enforces them per message type. [Source: architecture.md#adr-008] [Source: architecture.md#6-1-stix-link-messages-protocol-v1]
- Every Link request except `Hello` and `Auth` carries an authorised session. [Source: architecture.md#adr-008]

## Testing

<!-- LOCKED. STRATEGY ONLY — what to verify and how. Never run tests or quote coverage here. -->

- **Approach:** integration tests against the mock.
- **Key scenarios:** good login, bad password, Viewer trying to upload, expiry.
- **Per-AC verification:** AC #1 → roles property; AC #2 → build without QtKeychain works; with it, the token is reused; AC #3 → Viewer → Upload disabled; forced request → Forbidden shown; AC #4 → mock expires the token
- **Fixtures / mocks:** mock accounts: admin, engineer, viewer.
- **Edge cases to cover:** login while a request is pending.
