# 4.4: Install and remove `.stixpkg` locally

**Story ID:** 4.4  
**Epic:** 4 — Library packages and catalogue (editor)  
**Slug:** stixpkg-install-local  
**Status:** ready-for-dev   <!-- lifecycle: backlog -> ready-for-dev -> in-progress -> review -> done -->

> Owned by planning until `ready-for-dev`. Sized to one dev-day (~2-8h). No story points.

## Story

As **an integrator**,  
I want **to install a package file into STIx Config and remove it again**,  
so that **I can use new or updated blocks**.

## Acceptance Criteria

<!-- LOCKED. Numbered, testable. External dev tools must not edit. -->

1. `LocalRepository::install` unpacks a `.stixpkg` (zip) into `libraries/<Kind>/<Uuid>/<Vers>/`, verifying the SHA-256 of every file against `manifest.xml`.
2. Installing a version that is already installed with the same Sha256 is a no-op; with a different Sha256 it is refused (`InvalidArgument`: "same version, different build").
3. Installation is atomic: unpack to a temp folder, verify, then rename; a failure leaves nothing behind.
4. `remove(uuid, vers)` deletes that version; it is refused while an open project requires it.
5. Path traversal in zip entries (`../`) is rejected.

## Tasks / Subtasks

- [ ] Zip reading (QZipReader-equivalent or minizip, decided in the story) (AC: #1)
- [ ] Verify + atomic install (AC: #1, #2, #3, #5)
- [ ] Remove with the in-use check (AC: #4)
- [ ] Tests (AC: #1, #2, #3, #4, #5)

## Dev Notes

<!-- LOCKED. Cited guidance. [Inference] marks judgement calls not stated in the planning docs. -->

- A package is a zip `<Name>-<Vers>.stixpkg`; `SIGNATURE` covers the manifest and the SHA-256 of every file; identity = Uuid + Vers + Sha256 of the canonical zip. [Source: architecture.md#adr-004]
- Third-party dependencies beyond Qt need an ADR. If a zip library is required, keep it small (e.g. minizip-ng) and record the choice in decision-log.md. [Source: architecture.md#adr-013]
- Long-running work (package unpacking) runs off the GUI thread; results come back as queued signals. [Source: architecture.md#adr-009]
- Signature verification is the next story (4.5); here only the per-file hashes are checked. [Inference]

## Testing

<!-- LOCKED. STRATEGY ONLY — what to verify and how. Never run tests or quote coverage here. -->

- **Approach:** unit tests with crafted packages.
- **Key scenarios:** good package; tampered file; zip-slip; duplicate version.
- **Per-AC verification:** AC #1 → install, then the files exist; AC #2 → same-build no-op / different-build refused; AC #3 → kill mid-install (simulate) → no leftovers; AC #4 → remove while a project requires it → refused; AC #5 → `../evil` entry → refused
- **Fixtures / mocks:** packages built in the test from `tests/fixtures/packages/`.
- **Edge cases to cover:** an empty zip; a huge file.
