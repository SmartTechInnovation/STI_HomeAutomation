# 10.13: GPIO digital input/output driver plugin

**Story ID:** 10.13  
**Epic:** 10 — STIx Runtime MVP (separate repository `stix-runtime`)  
**Slug:** digital-io-driver  
**Status:** ready-for-dev   <!-- lifecycle: backlog -> ready-for-dev -> in-progress -> review -> done -->

> Owned by planning until `ready-for-dev`. Sized to one dev-day (~2-8h). No story points.

## Story

As **an installer**,  
I want **the controller's digital inputs and relay outputs to work as signals**,  
so that **a real switch can turn on a real light through the program**.

## Acceptance Criteria

<!-- LOCKED. Numbered, testable. External dev tools must not edit. -->

1. A driver plugin for the `DigitalIn` / `DigitalOut` sections uses Linux `libgpiod` (v2) with edge events; each `DigitalInCh` becomes a signal emitted with `emit_signal` on change, with a configurable debounce (default 20 ms).
2. `DigitalOutCh` writes are applied through the SDK queue adapter (non-blocking `write`).
3. Channel numbers map to GPIO lines through a per-device-model mapping file inside the package.
4. End to end on hardware: input edge → And block → relay output in < 5 ms.
5. Packaged as a `.stixpkg` for linux-aarch64 and linux-armv7hf.

## Tasks / Subtasks

## Dev Notes

<!-- LOCKED. Cited guidance. [Inference] marks judgement calls not stated in the planning docs. -->

- Each driver runs its own thread(s); when a value arrives it calls `emit_signal`, and callbacks run inline so the value reaches its targets at once. [Source: architecture.md#adr-005]
- Periphery schema sections `DigitalIn`/`DigitalOut` with channels `DigitalInCh`/`DigitalOutCh`. [Source: architecture.md#5-data-model]
- `write` must be thread-safe and non-blocking; use the SDK queue adapter. [Source: architecture.md#adr-005] [Source: architecture.md#adr-006]
- The hardware board / device models are not specified in the architecture; the first target board must be chosen and recorded in decision-log.md. [Inference]
